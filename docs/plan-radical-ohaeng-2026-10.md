## 2. 부수 기준 자원오행 정의안

### 2-1. 판정 순서 (글자 하나에 값 하나)

1. **정규화**
   - 호환 한자(U+F900~FAFF 등)는 NFKC로 통합 한자에 붙인다.
   - 값은 통합 한자 쪽에만 둔다. 호환 한자 85자 중 44자의 오행이 엇갈려 있던 것이 이 단계에서 사라진다.
2. **간지 예외**: 천간·지지 22자는 간지 오행을 쓴다. 甲木 乙木 丙火 丁火 戊土 己土 庚金 辛金 壬水 癸水 / 子水 丑土 寅木 卯木 辰土 巳火 午火 未土 申金 酉金 戌土 亥水. 공개 DB 세 곳이 모두 이렇게 한다.
3. **뜻 예외표**
   - 넣는 기준: 공개 DB 2곳 이상이 부수 기본값과 다르면서 **서로 같은** 값을 줄 때만 후보로 올린다. 사람이 검수해 확정한다.
   - 현재 후보는 54자다. 예: 南火 光火 兌金 尙金 五土 允土 玄火 盛火 益水.
   - 成처럼 DB끼리 갈리는 글자는 예외로 두지 않는다. 부수값을 쓰고 '이견'으로 표시한다.
4. **부수표**: 강희 부수 번호(Unihan kRSUnicode 첫 값)를 214부수표에 넣어 값을 정한다.
5. **부수 자료가 없으면** '미상'으로 둔다. 목표는 0자다. 405자 법원 코드는 이미 제외돼 있다.

**변형 부수는 따로 다루지 않는다.** kRSUnicode는 氵·水를 같은 85번으로 준다. 조사에서 변형과 원형은 같은 값을 받았다(氵忄扌衤⺼⺮艹辶阝王刂灬攵). 유일한 예외는 犭인데, 철학캠프만 犭을 水로, 나머지는 土로 봤다. 사이트는 土 하나로 간다.

**S/A/B/C/D 글자를 다시 쓰지 않는 이유**
- 옛 의미(S = "작명가 검수 완료")에 기대는 코드가 4곳 있다:
  - 관련도 S +100 (`HanjaData.cs:1400-1402`)

  - /hanja 정렬 GRADE_RANK
  - 획수 20의 C·D 감산
- 블로그 글에도 "검수 완료 S등급"이 박혀 있다.

**옛 등급에 기대던 곳은 '코어 여부'(`c:1`, Source == Core_v1)로 옮긴다.** 옛 S 2,054자는 코어 2,060자 안에 전부 들어 있으므로, 이렇게 옮기면 순서와 점수는 그대로다.

- /hanja 정렬 → 코어 먼저, 다음 획수.
- 획수 20의 C·D ×0.85 → 코어가 아니면 ×0.85. 이름이 "오행 판정 신뢰도"에서 "획수 자료 미검수"로 바뀐다. 코어는 강희 획수를 검수한 글자이므로 의미도 맞다.

### 2-5. 기존 뜻 기반 값: **지우지 않고 별도 필드로 둔다**(D4)

- **보존하는 것**
  - 백엔드: `MeaningElement`·`MeaningRationale`
  - 데이터: core_v1·radical_map 원본을 그대로 둔다.
  - hanja-seo.json에는 오행 값(`me`)을 싣지 않는다. 뜻 문장은 `mw`로 싣는다.
- **화면에 오행을 둘 보이지 않는다.** 한 글자에 오행이 두 개 보이면 이번 독자 같은 혼란이 다시 생긴다.
- **보존하는 이유**
  1. 2,060자를 검토한 자산이다. 뜻 문장 2,054개는 글자 페이지의 고유 본문이다. 다만 433개에 '금의 강직함' 같은 오행 단어가 있어서 그 부분은 걷어 낸다.
  2. 예외표를 검수할 때 참고 자료가 된다(뜻으로는 火인데 부수로는 木인 글자 목록).
  3. 독자 질문에 "예전에는 뜻으로 火라고 했다"고 설명할 근거가 된다.
  4. 되돌릴 때 원천이 된다.
- **화면 근거 섹션**
  - "오행 판정 근거"에는 부수 근거를 새로 생성한다. 예: "부수 扌(손 수) → 木. 손·나무 부수는 작명에서 木으로 봅니다."
  - 그 아래 "글자 풀이"에 `mw`를 둔다.

### 2-6. 데이터 모델 — 글자별 결과 파일 하나를 양쪽이 그대로 읽는다

- **새 파일 `data/hanja_resource_element.json`**: 글자 하나에 `{e, g, kn(부수 번호), k(부수 표기), alt, basis, w}`를 담는다.
  - 만드는 스크립트: `scripts/build_resource_element.py`
  - 입력: kRSUnicode 추출본, 부수표, 예외표, 이체자 맵
- **백엔드 HanjaData**
  - 이 파일을 **마지막에** 적용해 FiveElement를 덮는다.
  - core FE 덮어쓰기(`:849-850`)는 MeaningElement로 돌린다.
  - unihan.json FE 채움(`:1672-1678`)과 획수 AutoCalc FE(`:347-418`)는 끈다.
- **build_hanja_seo_data.py**는 오행을 계산하지 않는다. 같은 파일을 복사만 한다. 이로써 지금의 이중 구현(`:123-137`)이 없어진다.
- **보증 장치**
  - 새 CLI `dotnet run -- dump-hanja-elements`의 출력과 hanja-seo.json을 9,190자 전부 대조해 불일치 0을 확인한다. 지금은 1,718자가 어긋난다.
  - 이 대조를 감사 스크립트로 고정한다.
- **hanja-seo.json 필드**: `e`·`g`(새 코드)·`w`(부수 근거)·`k`·`kn`·`alt`·`mw`·`c`. `me`는 싣지 않는다. 늘어나는 크기는 수백 KB로 예상한다(1.25MB → 측정 필요).

## 7. 위험

### 7-1. 네이버 노출 (수천 쪽 동시 변경)

**바뀌는 범위**
- /hanja/[글자] 9,096쪽(네이버 색인, 구글은 googleBot noindex)
  - 메타 설명 약 6,000쪽(" · 오행 X")
  - 근거 문장 전부
- /hanja/[독음] 489쪽: 분포 문구 ≥292쪽, 불용 표시
- /name 공개 약 3,700쪽
  - 조합 81%
  - 메타 설명(mean) 342쪽

**바꾸지 않는 것**: URL·title 템플릿·robots·사이트맵 구성. 10/6에 네이버 −40%를 부른 것은 **색인 제외(일반 noindex)**였지 본문 수정이 아니었다. 다만 대량 동시 수정에 네이버가 어떻게 반응할지는 근거가 없어 알 수 없다.

**완화책**
1. 제목·URL·robots를 건드리지 않는다. 메타 설명의 틀도 유지하고 값만 바꾼다.
2. 나눠서 배포하지 않는다. /hanja와 /name이 서로 링크하므로, 반쯤 바뀐 상태가 더 큰 모순을 만든다.
3. 네이버 전용 사이트맵 lastmod를 갱신해 재수집을 유도한다.
4. 서치어드바이저 일별 노출을 14일간 관찰한다. **7일 평균이 직전 14일 대비 −25% 이하로 떨어지고 변동이 배포일과 맞으면** 원인을 조사한다. 롤백은 그다음에 판단한다(평소 요일 변동이 있으므로 하루 수치로는 판단하지 않는다).

### 7-2. 애드센스 재검토 시점

- 재검토는 **아직 요청 전**이다(10/21 기준). 심사 중 대수술 금지 원칙에 걸리지 않는다.
- 이번 전환은 정확성과 편집 글(정정 글, 새 리포트, /method 보강)을 늘린다. 재검토 근거로 쓸 수 있다.
- 요청은 배포 ≥14일 뒤에 한다. 구글 재크롤 기간이 필요하고, 그동안 변경을 멈춘 상태여야 한다.
- 글자 9,096쪽의 googleBot noindex는 유지한다. 승인 뒤 "S급 2,054자만 되살리기" 검토 항목은 "코어 2,060자"로 이름을 바꾼다.

### 7-3. 블로그와 사이트 불일치 기간

- 배포 전까지는 둘 다 옛 값이라 서로 맞는다. 다만 독자가 질문한 振·津처럼 작명소 기준과는 이미 어긋나 있다.
- 불일치는 배포 시점부터 덧붙임을 달 때까지 생긴다. 줄이는 방법:
  - 정정 글과 덧붙임 문구를 **S7에서 미리** 써 둔다.
  - 배포 당일 또는 다음 날 정정 글을 낸다.
  - 8편 덧붙임은 3일 안에 단다.
  - '은' 편은 7일 뒤에 단다(최장 불일치 구간).
- 독자 답글은 지금 보내도 된다. 기준 설명만 하고 사주 판단은 하지 않는다.
- 미발행 큐(21~23)는 부수표(D2)가 확정될 때까지 보류한다.

### 7-4. 그 밖

- **이견 기본값의 정당성**: 어떤 표를 택해도 일부 작명가와 다르다. 화면에 '이견 있음'과 대체값을 보이는 것이 핵심 방어다. "작명소 기준과 같다"가 아니라 "작명소들이 가장 많이 쓰는 값"이라고 쓴다.
- **조합 품질 회귀**: 새 1순위에 侐·烋 같은 어색한 글자가 올라올 수 있다. audit E 목록 두더지 검수(2~4라운드)를 S6 필수로 둔다.
- **mean 공백**: 배치 윤문 전에 빌드하면 공개 69명의 뜻이 빈다. 배치 완료 → 재빌드 → 빈 mean 0을 확인한 뒤에만 커밋한다.
- **운영↔로컬 차이 의심(미확인, 전환과 별개)**
  - 로컬 빌드 산출물(`bin/Debug/net10.0/data`)에 `data-gov.csv`·`data-naver.csv`가 없다. csproj의 `Content Update="data\**\*.*"`는 기존 Content 항목만 갱신하고 CSV를 새로 넣지 않는다.
  - 로컬 덤프는 `dotnet run`을 저장소 루트에서 돌리기 때문에 현재 폴더에서 CSV를 찾는다.
  - 운영(Docker publish, /app)에서는 `IsGovernmentListed`가 전부 false일 가능성이 높다. 그러면 관련도 +500이 빠지고, ThreeSyllableEngine Tier 2 필터가 비고, /evaluate 배정 한자가 로컬과 달라질 수 있다.
  - S8 운영 검증 전에 Render 로그나 운영 응답으로 확인한다. 맞으면 csproj에 `<Content Include="data\*.csv">`를 넣는 작은 수정이 필요하다.
- **병행 세션**: 블로그 초안·strategy.md를 다른 세션이 고칠 수 있다. 각 단계 시작 전에 `git pull`하고 인수인계를 다시 읽는다.
- **호환 한자 리터럴 함정**: 테스트·소스에 호환 한자를 글자로 쓰지 않는다(정수 코드포인트·`\u` 이스케이프). 저장 뒤 바이트를 확인한다.
- **대리값 한계**: §1-2의 수치는 실제 값의 73%만 대리값으로 덮은 추정이다. S4 직후 같은 스크립트(`plan/scripts/compare_combos.py`·`score_sim.py`)로 실측치를 다시 낸다.
